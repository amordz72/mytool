- [ ] `PROPOSED` **حفظ مؤقت للنص الأصلي بعد تحديث الصفحة**: لم يُحسم بعد. إن تم اعتماده، يفضّل Session Storage أو آلية جلسة مؤقتة، وليس حفظًا دائمًا، خصوصًا مع أكواد البطاقات.

- [ ] `PENDING` **الحفاظ على اسم الملف الأصلي عند وجوده**: إذا دخل المصدر كملف مرفوع، يُحفظ اسم الملف الأصلي ضمن الأرشيف أو الـManifest كما جاء من المورد، ولا يُفقد عند توليد الملفات الجديدة. إذا كان المصدر نصًا ملصوقًا فقط، يولّد MyTool اسم مصدر واضحًا مرتبطًا بالدفعة.
- [ ] `PENDING` **ربط المصدر والمخرجات بنفس Batch ID**: كل عملية معالجة تأخذ `Batch ID` واحدًا، ويظهر نفس الـID في اسم ملف المصدر الأصلي وكل ملفات TXT المشتقة منه، حتى يمكن الرجوع من بطاقة خاطئة إلى المصدر الأصلي بسهولة.
- [ ] `PENDING` **نفس التاريخ/الوقت للمجموعة كاملة**: المصدر الأصلي وكل الملفات الناتجة من نفس العملية تستعمل نفس Timestamp المولّد مرة واحدة عند بداية العملية، بدل توليد وقت مختلف لكل ملف.
- [ ] `PROPOSED` **اسم المصدر داخل بيانات/اسم الدفعة عند معرفته**: مثل وفرلي / OneClick / Mobilis / Token Store، بدون الاعتماد على اسم مستخدم WhatsApp، لتسهيل معرفة المورد أو الصيغة التي جاءت منها البطاقة.
- [ ] `PENDING` **الاحتفاظ بالمصدر محليًا على الهاتف أو الكمبيوتر**: الهدف إنشاء أرشيف محلي يسمح بالرجوع لاحقًا إلى النص/الملف الأصلي عند وجود بطاقة خاطئة ومراجعة المورد.
- [ ] `PROPOSED` **تنظيم الأرشيف حسب الشهر والمصدر/النوع**: مثال مبدئي `MyTool/2026-09/Waffarly/` أو `MyTool/2026-09/Mobilis/`، وداخلها الدفعات والملفات الأصلية والمخرجات. الهدف منع مجلد واحد ضخم وتسهيل الرجوع لشهر محدد أو مصدر محدد.
- [ ] `PROPOSED` **فهرس شهري محلي للبحث برقم البطاقة**: إنشاء ملف محلي مثل `index-2026-09.csv` أو JSON داخل مجلد الشهر، يربط رقم البطاقة باسم الملف الأصلي + Batch ID + المصدر + نوع البطاقة. هذا الفهرس يبقى على الجهاز فقط ولا يُرفع إلى GitHub، والهدف أن يكتب المستخدم رقم بطاقة خاطئة فيجد فورًا أي ملف/دفعة جاءت منها.
- [ ] `PROPOSED` **لا نحفظ أكواد البطاقات في localStorage كأرشيف دائم**: `localStorage` يبقى للإعدادات والبيانات الخفيفة فقط؛ الأكواد والنصوص الأصلية تحفظ كملفات محلية. إذا احتجنا كاشًا مؤقتًا داخل المتصفح لاحقًا، ندرس `IndexedDB` بمدة قصيرة مثل 7–30 يومًا، لكن لا نعتمد عليه كأرشيف رئيسي لأن بيانات المتصفح قد تُمسح أو تفقد.
- [ ] `PROPOSED` **مدة الاحتفاظ بالفهرس المحلي**: الفهرس الشهري على الملفات يمكن الاحتفاظ به طويلًا حسب مساحة الجهاز، بينما أي كاش متصفح مؤقت - إن استُخدم - يكون محدودًا زمنيًا وقابلًا للمسح تلقائيًا بعد 7 أو 30 يومًا. لا نحذف الملف الأصلي تلقائيًا إلا بقرار واضح من المستخدم.
- [ ] `PROPOSED` **مسار حفظ خاص بـ MyTool**: إضافة إعداد لمسار/مجلد أرشيف خاص بالمشروع، مثل مجلد `MyTool` يختاره المستخدم مرة واحدة إذا كان المتصفح/النظام يدعم الوصول إلى المجلدات.
- [ ] `PROPOSED` **التحقق من مسار الحفظ قبل الأرشفة**: إذا كان المسار المحفوظ غير متاح أو فقد الإذن، لا يدّعي البرنامج أن الأرشفة تمت؛ يوقف الأرشفة ويطلب من المستخدم إعادة اختيار المجلد أو إنشائه إذا كان ذلك مدعومًا.
- [ ] `PROPOSED` **إنشاء المجلد عند الإمكان**: إذا كانت واجهة المتصفح/النظام تسمح بإنشاء مجلد داخل المسار المختار، يمكن عرض خيار إنشاء مجلد MyTool تلقائيًا؛ وإلا يطلب من المستخدم اختياره يدويًا.
- [ ] `PROPOSED` **Fallback للمتصفحات التي لا تدعم مسارًا دائمًا**: إذا لم يدعم الهاتف/المتصفح File System Access أو حفظ صلاحية المجلد، يبقى الخيار الآمن هو تنزيل المصدر الأصلي مع الملفات المشتقة إلى Downloads، مع نفس Batch ID والتاريخ، بدل ادعاء وجود مسار دائم.
- [ ] `PROPOSED` **فهرس محلي للدفعات لاحقًا**: يمكن لاحقًا حفظ Metadata غير حساسة عن الدفعات (Batch ID، التاريخ، نوع المصدر، أسماء الملفات) بدون حفظ الأكواد نفسها في LocalStorage، لتسهيل البحث عن الملف الأصلي.

> الهدف من هذه المجموعة: إذا ظهر لاحقًا كود بطاقة خاطئ، نعرف الدفعة والمصدر ونرجع إلى الملف أو النص الأصلي بدل البحث اليدوي بين الرسائل والتحميلات.

## تحسينات واجهة ما زالت غير منفذة

- [ ] `PENDING` **إزالة Checkboxes الإعدادات من الصفحة الرئيسية نهائيًا**: خيارات «إزالة الفراغات» و«التعرف التلقائي» وأي خيار مشابه تكون إدارتها من صفحة `settings.html` فقط، ولا تظهر داخل واجهة المعالج الرئيسية. المطلوب حذف/عدم إنشاء عناصر التحكم المكررة من الواجهة الأساسية بدل الاعتماد فقط على إخفائها بـJavaScript أو CSS، لأن ظهورها في بعض النسخ/الكاش يسبب زحمة وتكرارًا. تبقى القيم محفوظة في `localStorage` وتقرأها المعالجة من الإعدادات.
- [ ] `PENDING` **إخفاء أدوات التقسيم فعليًا عندما يكون النوع غير مفعّل من الإعدادات**: إعداد إظهار/إخفاء التقسيم موجود بالفعل، لكن المطلوب تقوية التنفيذ بحيث إذا كان التقسيم معطّلًا لنوع مثل وفرلي/OneClick أو Token Store أو Idoom فلا تُنشأ واجهة التقسيم أصلًا في النتيجة، بدل أن تُنشأ ثم تُخفى لاحقًا بـJavaScript. الهدف منع ظهورها لحظة قصيرة أو رجوعها بسبب الكاش/تأخر السكربت. Mobilis يبقى حسب إعداد المستخدم، وباقي الأنواع لا يظهر لها التقسيم إلا إذا فُعّل صراحة من صفحة الإعدادات.
- [ ] `PENDING` **ضغط وتجميع أزرار التحكم الرئيسية لتقصير الواجهة**: إعادة ترتيب أزرار «رفع ملف» و«الإعدادات» و«تحديث» بحيث لا يأخذ كل زر سطرًا كاملًا وعرض الصفحة. المقترح المبدئي: شريط أدوات مدمج صغير أعلى مربع النص؛ «رفع ملف» زر أساسي متوسط، «الإعدادات» زر صغير بأيقونة ترس، و«تحديث» زر ثانوي صغير/أيقونة لأن المعالجة أصلًا تلقائية. على الهاتف توضع الأزرار في صف واحد أو صفين قصيرين حسب العرض، مع تقليل الارتفاع والـpadding بدون التضحية بوضوح اللمس. لا يُغيّر هذا التعديل منطق المعالجة، بل الشكل والمكان فقط.
- [ ] `PENDING` **أسماء ملفات قصيرة ومميِّزة للهاتف**: أسماء ملفات النتائج يجب أن تبدأ بالمعلومة التي يحتاجها المستخدم عند الاختيار من مدير الملفات، لأن Android يختصر نهاية الاسم. في بطاقات Free Fire مثلًا لا يبدأ الاسم بـ`WAFFARLY_Garena-Free...` لأن ملفات 100 و200 جوهرة تظهر متشابهة؛ الأفضل أن تبدأ الفئة/القيمة أولًا ثم المصدر باختصار، مثل `FF100_WAF_...txt` و`FF200_WAF_...txt`. نفس المبدأ يطبق على الأنواع الأخرى مثل `MOB1000_...` و`MOB2000_...`. يفضّل أن يظهر العدد بعد القيمة، ثم المصدر/التاريخ أو Batch ID في النهاية. الهدف أن يعرف المستخدم من شاشة اختيار الملف وحدها أي ملف يخص 100 أو 200 جوهرة بدون فتحه أو الرجوع بين الشاشات. لا تغيّر هذه المهمة محتوى البطاقات، فقط Naming Convention للمخرجات.
- [ ] `PROPOSED` **إظهار الفئة/القيمة بوضوح داخل بطاقة النتيجة قبل التحميل**: بجانب زر TXT يظهر Label واضح مثل `Free Fire • 100 Diamonds • Waffarly` أو `Mobilis • 1000 DA` حتى تكون القيمة مؤكدة قبل تنزيل الملف، مع إبقاء اسم الملف المختصر متوافقًا معها.
- [ ] `PROPOSED` **تجربة Theme/CSS خفيف لـ MyTool**: تجربة قالب بصري مجاني وخفيف لتحسين شكل الواجهة واكتساب خبرة عملية مع الـTemplates، لكن بدون إدخال Framework ثقيل أو مكتبات كبيرة قد تبطئ الأداة.
- [ ] `PROPOSED` **تجربة القالب بشكل معزول أولًا**: الأفضل عمل صفحة/نسخة تجريبية أو طبقة CSS منفصلة قبل تغيير الواجهة الأساسية، ثم الاحتفاظ فقط بالأجزاء الناجحة (الأزرار، البطاقات، التنقل، النوافذ، الإعدادات) بدل تحميل Theme كامل إذا كان ثقيلًا.
- [ ] `PROPOSED` **فصل الشكل عن منطق المعالجة**: أي Theme مستقبلي لا يغيّر Parser أو قواعد Mobilis/وفرلي/Token Store أو التنزيل؛ يكون تغييرًا بصريًا فقط قدر الإمكان حتى يسهل استبداله لاحقًا.
- [ ] `PROPOSED` **مراجعة تجربة التحميل المتعدد على متصفحات الهاتف**: إذا منع المتصفح تنزيل عدة ملفات متتابعة، ندرس خيار ZIP واحد يحتوي ملفات TXT منفصلة بدل دمج البطاقات في ملف واحد.

- [ ] `PROPOSED` **ملخص تحقق مختصر فوق النتائج**: سطر واحد مثل `5 بطاقات • فئتان • 0 مكرر • المصدر: وفرلي`، مع حالة خضراء عند سلامة الدفعة أو تحذير واضح عند وجود مشكلة. الهدف أن يعرف المستخدم نتيجة القراءة كاملة قبل الضغط على التحميل.
- [ ] `PROPOSED` **ملف Manifest صغير لكل Batch**: ملف نصي/JSON محلي بدون تغيير محتوى ملفات البطاقات، يحتوي Batch ID والتاريخ ونوع المصدر وأسماء الملفات الناتجة وعدد البطاقات في كل ملف. يفيد في الرجوع للمصدر ومعرفة ما تم توليده حتى لو تغيرت أسماء الملفات أو نُقلت لاحقًا.
- [ ] `PROPOSED` **زر «دفعة جديدة» بعد انتهاء العمل**: يمسح النص والنتائج واسم الملف وحالة الدفعة الحالية بشكل صريح بعد تأكيد المستخدم، ويبدأ Batch جديدًا بدل بقاء البيانات القديمة واحتمال خلطها مع لصق جديد.

## قاعدة تسجيل الاقتراحات

أي اقتراح أو تحسين مفيد يظهر أثناء العمل ولم يُنفذ فورًا يجب تسجيله هنا أو في المرجع الأنسب داخل المستودع بحالة `PROPOSED` أو `PENDING` قبل الانتقال عنه. عند تنفيذه تُحدّث حالته إلى `IMPLEMENTED`، وبعد الاختبار العملي إلى `TESTED`.

## قاعدة مهمة

المصدر الأصلي = Raw Source، ويجب اعتباره للقراءة فقط أثناء المعالجة.
أي Trim أو Normalize أو استخراج أو تنظيف يتم على نسخة مشتقة داخل المعالج. لا يغيّر المصدر الأصلي إلا بفعل صريح من المستخدم.

لا تعتبر أي مهمة منجزة حتى تكون موجودة فعلًا في الكود، وبعدها تُغيّر حالتها إلى `IMPLEMENTED`، وبعد اختبارها عمليًا إلى `TESTED`.
